# 웨이크업 계획 — STM32 가 깨우고 모으고, FPGA 가 판단한다 (2026-10-25)

> 상태: **계획** (코드 변경 없음). 결정: **방식 B** (사용자 승인 2026-10-25).
> 보드: 사용자 제작 `KWS_Layout_STM32` (4층, 100×100 mm). 핀은 거버 X2 넷 이름에서 복원.

## 0. 요점

지금 FPGA 는 **always-on** 이다: 비교기 16가닥을 계속 받고, 언제 `start` 를 줄지는
슬라이딩 창으로 풀려고 했다 (`windowing_plan.md`). 방식 B 는 그 질문을 **STM32 로 옮긴다**.

```
AFE ──16가닥(1.8 V)──▶ STM32L476 ──UART + WAKE──▶ FPGA (kws_top, 칩 검증 완료)
       J5 → PB0..15      평소 Stop 2                  받은 클립 1개를 분류
                         소리 → 깨어남 → 1 s 취득       결과를 UART 로 돌려줌
```

- **FPGA 의 신경망은 그대로다.** `kws_top` 은 원래 `in_valid / in_frame` 으로 프레임을
  받는다. 지금은 `kws_frame_ctrl` 이 비교기에서 만들어 넣고, B 에서는 UART 로 받은 프레임을
  넣는다. 600/600 검증된 데이터패스를 손대지 않는다.
- **"언제 시작하나"는 STM32 의 트리거가 정한다.** FPGA 는 받은 것만 처리한다.
- ⚠️ **전력의 한계**: 키트의 FPGA 는 전원을 끌 수 없어 정적 0.094 W 가 계속 흐른다.
  B 가 줄이는 것은 FPGA 의 동적 전력과 "항상 계산" 뿐이다. 진짜 저전력은 추론까지
  STM32 로 옮기는 방식 A — B 가 돈 뒤의 비교 실험으로 남긴다 (§7).

## 1. 보드 (확정된 것)

| 블록 | 연결 | 비고 |
|---|---|---|
| 전원 | J1 3V3 → TPS7A2018 → **1.8 V** | STM32 전체가 1.8 V |
| 비교기 | J5(2×10) `v_comp_k` → **PBk** (k=0..15), GND 4핀 | AFE 1.8 V 출력에 직결 |
| FPGA 링크 | J4(1×4): UART_TX · UART_RX · WAKE_FPGA · GND | TXU0304 로 1.8 V ↔ JP3 (FPGA 면 **3V3**) |
| UART | PA2/PA3 (USART2, LPUART1 도 가능) | **JP1/JP2 로 FPGA 쪽 또는 ST-LINK 가상 COM 중 하나** |
| WAKE | PA8 → 시프터 → WAKE_FPGA | 100k 풀다운 |
| 디버그 | J3 STDC14 (SWD + 가상 COM) | SWO 불가 (PB3 = ch3) |
| 클럭 | LSE 32.768 kHz, HSE 없음 | MSI → PLL 80 MHz |

**설계상 이점 둘**: (1) `GPIOB->IDR` 한 번 읽기 = 프레임 워드 (bit k = ch k, FPGA 와 같은
포맷). (2) 채널마다 다른 핀 번호 → **EXTI 라인 16개를 채널별로** 쓸 수 있다.

**펌웨어에서 챙길 것**: PB3·PB4 는 리셋 직후 JTAG 핀이다 (PB4 는 내부 풀업 → 설정을 빠뜨리면
**ch4 가 늘 1**). CubeMX 에서 Debug = Serial Wire, PB3/PB4 = GPIO_Input.

**제약 둘**: 보드에 **LED 가 없고**, UART 가 **하나뿐**이라 FPGA 와 통신하는 동안은 PC 로
로그를 못 낸다. 디버깅은 SWD(변수 감시) 또는 FPGA 키트의 LED/7-세그먼트로 한다.

## 2. STM32 펌웨어 — 상태 3개

```
 IDLE (Stop 2) ──트리거──▶ CAPTURE (1 s, 100 프레임) ──▶ SEND (UART) ──▶ IDLE
      ▲                                                        │
      └──────────────── 결과 수신 / 타임아웃 ──────────────────┘
```

### 2.1 프레임 하나를 만드는 법 — FPGA 의 sticky OR 과 같게

모델의 이산화 규칙은 "10 ms 안에 **한 번이라도** 1 이었으면 1" (CLAUDE.md §2.8). FPGA 는
이것을 sticky OR 로 한다 (`kws_frame_ctrl`). STM32 에서는:

```
프레임 시작:   seen = GPIOB->IDR          ← 지금 켜져 있는 채널 (경계를 넘어 계속 1 인 경우)
프레임 동안:   EXTI 상승 에지 k → seen |= (1 << k)   ← 그 사이에 켜진 채널
프레임 끝:     frame[t] = seen
```

**에지만 보면 틀린다**: 프레임 경계를 넘어 계속 1 인 채널은 다음 프레임에 에지가 없다.
시작 시점의 레벨을 넣어야 "그 프레임 안에서 한 번이라도 1" 과 같아진다. EXTI 는 비동기 에지
검출이라 1 ms 미만 펄스도 놓치지 않는다.

### 2.2 10 ms 시간축

LPTIM1 을 LSE 로 돌린다 (Stop 2 에서도 동작). 32768 / 100 = 327.68 틱이라 정확히 10 ms 가
안 나온다 — 328 틱(10.0098 ms, +0.1%)으로 두거나 327/328 을 번갈아 쓴다. 모델의 STFT hop
(10 ms)에 0.1% 는 무의미하다고 보지만, §5 의 프레임 비교로 확인한다.

### 2.3 트리거 — 가장 큰 결정

| 모드 | 동작 | 장점 | 문제 |
|---|---|---|---|
| **M1 순수 이벤트** (Cerutti) | Stop 2 에서 EXTI 16개 대기 → 첫 에지에 깨어 바로 1 s 취득 | 가장 단순, 대기 전력 최소 | 잡음 에지 하나에도 깸 · **단어가 창 왼쪽 끝에 붙는다** |
| **M2 링 버퍼** | Stop 2 에서 LPTIM 이 10 ms 마다 깨워 프레임 1개를 링(예: 30 프레임)에 저장 → 프레임 조건(예: 켜진 채널 ≥ k)이 맞으면 링 + 나머지로 1 s 를 채움 | **사전 버퍼**로 단어 위치를 학습 분포에 맞출 수 있음 · 트리거 조건을 소프트웨어로 자유롭게 | 초당 100번 깸 (짧게) |

**정렬 문제**: GSC 클립에서 단어는 1 s 창 어딘가(대개 가운데 근처)에 있다. M1 은 단어 시작이
창 시작에 붙으므로 학습 분포와 다르다. 대응은 (a) M2 의 사전 버퍼 길이로 맞추기,
(b) 트리거 정렬 클립으로 파인튜닝(`partial75` 와 같은 방식).

> **첫 시뮬 결과 (2026-10-26, `bd_base`, val 768 클립)** — 가정이 깨졌다. GSC 무음
> (`_silence_`, 배경잡음 녹음) 에서 비교기가 **프레임의 15~89% 동안 켜져 있다** (ch15 89%,
> ch2·ch10 79%). 그래서 절대 조건(k 개 이상 켜짐)은 k=1~4 어느 것이든 잡음 자체로 충족되고,
> 3 s 스트림에서 캡처가 쉬지 않고 이어졌다 (깨는 횟수 ≈ 3.0) — **잠들지 못한다.**
> 그 표의 pre 순위도 무효다: 매 캡처 직후 다시 트리거되면 두 번째 창이 늘 `108 − pre` 에서
> 시작해, pre=10 이 목표와 2 프레임 안으로 **산술적으로** 맞았다.
> → 도구를 고쳤다: 단어 앞 무음 길이를 무작위로, **상대 트리거**(켜진 수 ≥ 배경 EMA + Δ)
> 추가, 무음 스트림에서 깨어 있는 비율(duty) 측정. 실제 조용한 방의 발화율은 이보다 낮을 수
> 있다 — 그건 하드웨어로 재야 한다 (단계 4).
>
> **원인 (2026-10-26)**: GSC `_silence_` 는 조용한 방이 아니다. `_background_noise_` 6개
> (**백색·분홍 잡음**, 설거지, 운동기구, 수돗물, 고양이)를 **녹음 음량 그대로** 잘라 만들고
> 10% 만 진짜 0 이다 (`data/speech_commands.py::synthesize_silence`). 고정 임계 아래서
> 백색잡음은 16채널을 다 켠다 (무음 on-count p90 = 16). 어떤 에너지 트리거도 여기서는
> 잠들 수 없고, 그게 맞다. → 질문을 바꿨다: **잡음이 키워드 대비 몇 dB 아래일 때 잠드는가.**
> `eval_trigger --noise zero -40 -30 -20 -10 gsc`.

**결정 기록 (2026-10-26) — 트리거 규칙: `k1_d4_run1_pre30` (M2, 상대 트리거)**

```
10 ms 마다:  on = popcount(frame)                      (16채널 전부)
             소리 = on >= 1  그리고  on >= bg + 4
             소리가 아니면  bg += (on - bg) / 32         (조용한 프레임에서만 배경 학습)
소리 프레임 1개 → 트리거. 캡처 = 그 프레임 300 ms 앞부터 1 s (링 버퍼 30 프레임)
캡처 후 80 ms (전송 + 추론) 동안은 다시 트리거하지 않음
```

val 에서 120개 정책 중 골랐다 (`eval_trigger`, 768 클립). 키워드 recall 은 세 후보가
표준오차(~1.5pp) 안에서 갈리지 않아 **오경보와 duty** 로 골랐다: Δ=2 는 −20 dB 에서
오경보가 4~5배, Δ=3·run3·pre20 은 −30 dB 에서 0.817 로 기준(0.83) 미달. **test 1회**:

| 잡음 (키워드 대비) | recall | 같은 표본 가운데 창 대비 | 무음 duty | 오경보/스트림 |
|---|---:|---:|---:|---:|
| zero / −40 dB | 0.806 | +0.3pp | 0 | 0.029 |
| −30 dB | 0.795 | −0.8pp | 0 | 0.032 |
| −20 dB | 0.792 | −1.1pp | 0.037 | 0.089 |
| −10 dB | 0.770 | −3.3pp | 0.068 | 0.085 |
| GSC `_silence_` 그대로 | 0.717 | — | **0.579** | 0.436 |

(2026-10-28: **펌웨어 정수 산술로 다시 잰 값** — `bg_q = 32 × 평균`, 32칸 워밍업.
`firmware/stm32_wake/core/wake_core.c` 가 이 시뮬레이터와 프레임 단위로 같음을 테스트로
확인했으므로 이 표가 보드에 들어가는 코드의 숫자다. float 판(2026-10-26)과의 차이는 전부
표준오차 안: −10 dB recall 0.761 → 0.770, duty 0.085 → 0.068, 나머지 ±0.01 이내.)

(test 표본의 가운데 창 키워드 정확도 0.803 — val 0.859 보다 낮은 것은 표본 차이다.
duty·오경보는 val 과 거의 같다.)

**읽는 법**: −30 dB 이하에서는 트리거가 정확도를 거의 안 깎는다. 보통 실내(−20 dB,
말소리 60 dB SPL 기준 약 40 dB SPL — 어림)에서 1pp, −10 dB 에서 4pp. 백색잡음급에서는
잠들지 못해 always-on 이 된다 — **전력 절감은 환경에 따라 달라지는 성질**이다.
Cerutti 식 절대 트리거(첫 에지)는 −30 dB 부터 무너진다 (val: duty 0.69, recall 0.750) —
ch15 의 임계가 0 에 가까워 약한 잡음에도 켜지기 때문이다.

**권장: M2 로 시작, M1 은 비교용.** 어느 쪽이든 §4 단계 1 에서 **하드웨어 없이 정확도를 먼저
잰다.**

### 2.4 SEND

WAKE_FPGA 를 올림 → 패킷 전송(§3) → FPGA 결과 수신(타임아웃 있음) → WAKE 내림 →
쿨다운(같은 단어로 다시 깨지 않게) → IDLE.

## 3. STM32 ↔ FPGA 프로토콜 (초안 — `docs/ICD.md` 에 새 절로 올릴 것)

```
STM32 → FPGA   0xA5 | N (=100) | frame[0..N-1] (각 2 바이트, little-endian, bit k = ch k) | CRC-8
FPGA → STM32   0x5A | class_idx | keyword_idx | margin (2 바이트) | CRC-8
```

- **패딩은 FPGA 가 한다.** STM32 는 native 100 프레임만 보낸다. 앞뒤 −1 패딩 14 칸 (`T=128`)
  은 모델 기하라 `parameters.vh`(manifest) 에서 와야 한다. 펌웨어가 모델 크기를 알면 재학습마다
  펌웨어를 고쳐야 한다. FPGA 는 `N == KWS_NATIVE_T` 를 확인하고 아니면 버린다.
- 200 바이트: 115200 baud 로 ~17 ms, 1 Mbaud 로 ~2 ms. 추론(57.4 ms) 대비 무시 가능.
- **WAKE 는 패킷 경계 신호로도 쓴다**: 올라가면 수신기 상태 초기화. UART 가 어긋나도 다음
  패킷에서 자동 복구된다. 나중에 FPGA 클럭 게이팅(BUFGCE)의 enable 로도 쓸 수 있다.

## 5. 왜 이 순서인가

- **정확도를 먼저 잰다.** 트리거 정렬은 하드웨어가 아니라 데이터 문제다. 보드를 다 만든 뒤에
  "깨는 건 되는데 정확도가 60%" 를 발견하면 늦다. 단계 1 은 GPU 만 있으면 된다.
- **링크를 AFE 와 분리해 검증한다.** 단계 3 은 입력이 골든 벡터라 답이 정해져 있다. 여기서
  틀리면 원인은 UART·패킷·패딩 중 하나다. 단계 4 에서 AFE 를 붙였을 때 틀리면 원인은 취득뿐이다.
  칩 자체검사에서 쓴 "한 번에 하나만 새로 붙인다" 와 같다.
- **취득은 FPGA 와 비교해 검증한다.** `kws_frame_ctrl` 은 이미 검증된 기준이다. 같은 신호를 두
  쪽이 동시에 받으면 STM32 의 프레임 생성이 맞는지 정답지가 생긴다.

## 6. 열린 질문

1. ~~J4 → J6 EXT 핀~~ — 확정 (2026-10-28): J4.2 UART_TX → J6 핀 30 (EXT27, `uart_rx`), J4.1 UART_RX ← J6 핀 31 (EXT28, `uart_tx`), J4.3 WAKE_FPGA → J6 핀 32 (EXT29, `wake`), J4.4 GND — J6 핀 49/50. STM32 보드 JP1·JP2 = 시프터 쪽, JP3 = 3V3. `rtl/constraints/kws_top.xdc`.
2. ~~AFE 기판이 비교기를 J5 와 J6 에 동시에 내보낼 수 있나?~~ — 아마 안 된다 (사용자). 단계 4 를 따로 캡처 + 통계 비교로 바꿨다.
3. M2 의 링 길이·트리거 조건(켜진 채널 수 k, 연속 프레임 수) — 단계 1 에서 정한다.
4. 결과를 어디에 표시하나 — FPGA 키트 LED/7-세그먼트가 가장 쉽다 (STM32 보드에는 LED 없음).
5. UART 속도 — 115200 으로 시작, 시프터(TXU0304)·배선이 허용하면 1 Mbaud.

## 7. 그다음 — 방식 A 와의 비교

B 가 돌면 같은 보드에서 **J4 를 안 쓰고** 추론까지 STM32 에서 하는 A 를 붙일 수 있다.
가중치 ~47 KB (플래시 1 MB), 80 MHz Cortex-M4 에서 수십 ms (추정, M4 에 popcount 명령 없음).
검증은 같은 골든 벡터로 비트 일치. 그러면 **같은 모델의 MCU 대 FPGA 지연·에너지**를 잴 수 있다.
