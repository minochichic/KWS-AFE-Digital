kws_frame_ctrl 사이클 실행기

설계 전체에서 비동기 신호를 만지는 모듈은 이것 하나뿐이다. 왼쪽에는 클럭이 없는 비교기 16가닥이 있고, 오른쪽에는 완전히 동기화된 [16,128] 텐서가 있다. 그 사이를 플립플롭 50개 남짓이 잇는다. 모든 신호를 한 클럭씩 본다.

리셋 상태다. 클럭 1을 누르면 rst_n 이 두 클럭 낮게 있다가 풀리고, 그 다음 클럭에 start 가 한 번 뜬다.
그림의 숫자는 줄여 놓았다. 실제 값은 FRAME_CYCLES=1,000,000, NATIVE_T=100, PAD_LEFT=PAD_RIGHT=14, T=128 — 100 MHz 에서 10 ms 프레임이라 프레임 하나가 백만 클럭이고 눈으로 볼 수가 없다. rtl/tb/tb_frame_ctrl.v 도 같은 이유로 줄여서 돌린다. 구조는 그대로다.

신호 사전

포트 8개와 내부 레지스터·와이어 11개가 전부다. 폭이 [15:0] 인 것은 채널마다 한 비트이고, 위 실행기에서 정사각형 16칸으로 나온다.

포트 — 모듈 밖과 주고받는 것
신호폭 / 방향뜻
clk1 · in시스템 클럭 100 MHz. 안쪽 모든 것이 이 상승 에지에만 움직인다
rst_n1 · in비동기 리셋(active-low). 0 이면 레지스터가 전부 초기값으로 간다
start1 · in한 클럭짜리 펄스. "클립 하나 시작" — S_IDLE → S_PADL
cmp[15:0]16 · in비교기 16가닥. 비동기. cmp[k]=1 = ch k 엔벨로프가 지금 임계값 위 (ICD §3)
out_ready1 · in소비자(conv1)가 "이번 클럭에 받을 수 있다"
out_valid1 · out"이번 클럭의 out_frame 은 진짜다"
out_frame[15:0]16 · out프레임 하나 = 16비트, 채널당 1비트. 0 은 아래쪽에서 −1 로 매핑된다
busy1 · out클립 진행 중 (st != S_IDLE)
내부 — 레지스터와 와이어
신호폭 / 종류뜻
cmp_in[15:0]16 · wireCMP_INVERT 가 1 이면 ~cmp, 아니면 cmp. 극성 반전을 흡수하는 자리
sync1[15:0]16 · reg동기화 1단. 여기가 메타스테이빌리티에 걸릴 수 있는 유일한 곳
sync2[15:0]16 · reg동기화 2단. 이제부터 믿고 쓸 수 있는 cmp
fc20 · reg프레임 안에서 도는 카운터, 0 … FRAME_CYCLES−1
frame_edge1 · wire(st==S_RUN) && (fc==FC_LAST) — 창이 지금 닫힌다는 한 클럭
sticky[15:0]16 · reg창 누적 OR. 한 번 선 비트는 창이 끝날 때까지 안 내려간다
held[15:0]16 · reg내보내려고 붙잡아 둔 프레임. frame_edge 에서 sticky 를 퍼낸 것
st3 · regS_IDLE / S_PADL / S_RUN / S_PADR
cnt8 · reg현재 단계에서 몇 장 내보냈는지
pending1 · reg"건네줄 프레임이 있다"
take1 · wirepending && out_ready — 악수가 성립한 클럭
held 가 sticky 와 따로 있는 이유. 창은 정확히 FRAME_CYCLES 마다 닫히는데 소비자는 아무 때나 바쁠 수 있다. sticky 를 바로 내보내면 소비자를 기다리는 동안 다음 창의 펄스가 섞인다. 퍼내는 순간과 건네는 순간을 분리한 것이다.

sticky OR — 이게 축약 규칙 그 자체다

레지스터에 입력을 매 클럭 OR 로 누적하고, 창 경계에서만 지운다. 한 번 선 비트는 창이 끝날 때까지 안 내려간다 — 그래서 "끈끈한(sticky)" OR 이다. 쓰는 이유가 세 겹이다.

1 · 근사가 아니라 규칙이다

CLAUDE.md 2.8 이 정한 이산화는 "창 안에서 한 번이라도 1 이면 1" (reduce = max)이다. {0,1} 위에서 max 는 정확히 OR 이므로 여기엔 구현할 것이 없다. 소프트웨어는 max-pool → threshold 순서인데 max 가 단조라 threshold → OR 과 같다 — 학습한 함수와 하드웨어가 계산하는 함수가 같다.

2 · 샘플링을 안 해도 된다

비교기 펄스는 수백 µs, 창은 10 ms 다. 창마다 한 번 들여다보는 방식이라면 그 순간 안 서 있는 펄스를 통째로 놓친다. sticky OR 은 매 클럭 (10 ns) 보고 기억한다. 언제 오든 못 놓치고, 값은 플립플롭 16개다.

3 · 경계에 프로토콜이 없어도 된다

결과가 "창 안 어디에서" 울렸는지에 의존하지 않는다. 그래서 아날로그는 우리 창이 어디 있는지 알 필요가 없고, 클럭을 공유하지 않으며, FPGA → 아날로그 신호가 0개다. 채터링도 무해하다 — 50번을 떨어도 OR 결과는 깨끗한 펄스 하나와 같은 1 이라, 히스테리시스가 정확도 요구사항이 아니다(ICD §4).

대가 · 정보를 일부러 버린다

펄스 개수·시각·지속시간이 전부 지워진다. 1개든 5개든 결과는 1. count 나 mean 은 그걸 살리지만 입력이 이진이 아니게 되어 Conv1 의 하드웨어 이점이 사라지고, threshold 와 순서 교환도 성립하지 않는다. 구현 한계가 아니라 설계 결정이다.

Verilog 한 줄이 그림에서 어디인가

네 덩어리뿐이다. 위 실행기에서 각 줄이 무엇을 움직이는지 대조해 보면 된다.

wire [15:0] cmp_in = CMP_INVERT ? ~cmp : cmp;

(* ASYNC_REG = "TRUE" *) reg [15:0] sync1;
(* ASYNC_REG = "TRUE" *) reg [15:0] sync2;

always @(posedge clk or negedge rst_n)
  if (!rst_n) begin
    sync1 <= 0;  sync2 <= 0;
  end else begin
    sync1 <= cmp_in;
    sync2 <= sync1;
  end

1. 2단 동기화기

cmp 는 우리 클럭과 아무 관계가 없다. 클럭 에지 바로 그 순간에 값이 바뀌면 sync1 은 0 도 1 도 아닌 중간 전압에 걸릴 수 있다 (메타스테이빌리티). 한 클럭을 더 주면 그 사이 안정되고 sync2 는 깨끗한 값을 본다. 파형에서 cmp → sync1 → sync2 가 한 클럭씩 밀려 있는 게 이것이다.

16채널이 한 줄인 이유: 반복문이 아니라 플립플롭 16개가 물리적으로 나란히 있는 것이다. 서로 기다리지 않는다.

always @(posedge clk or negedge rst_n)
  if (!rst_n || start) sticky <= 0;
  else if (frame_edge) sticky <= 0;
  else if (st == S_RUN) sticky <= sticky | sync2;

2. sticky OR

지우는 시점이 프레임 경계뿐이라는 게 핵심이다. 창 중간에 지우면 그 앞의 펄스가 사라진다.

파형에서 sticky 가 sync2 의 첫 1 을 따라 올라간 뒤 다음 frame_edge 까지 계속 높게 있는 것을 보면 된다.

wire frame_edge = (st == S_RUN) && (fc == FC_LAST);

S_RUN: begin
  fc <= (fc == FC_LAST) ? 0 : fc + 1;
  if (frame_edge) begin
    held    <= sticky | sync2;
    pending <= 1'b1;
  end
  ...
end

3. 프레임 타이머

fc 가 FRAME_CYCLES 를 세면 창이 닫힌다. 그때 sticky 를 held 로 퍼내고 pending 을 올린다.

sticky | sync2 인 이유: 논블로킹이라 frame_edge 시점의 sticky 에는 그 사이클의 sync2 가 아직 안 들어가 있다. 그냥 퍼내면 한 사이클을 잃고, 지울 때 0 대신 sync2 를 넣으면 다음 창이 또 센다. 이렇게 하면 모든 사이클이 정확히 한 창에 들어간다.

wire take = pending && out_ready;

if (take) begin
  out_valid <= 1'b1;
  out_frame <= held;
  pending   <= 1'b0;
  cnt       <= cnt + 1;
end

4. 악수 (handshake)

pending 은 "내보낼 프레임이 있다", out_ready 는 "받을 수 있다". 둘 다 참인 사이클에만 프레임이 건네진다. 소비자가 바쁘면 저절로 기다린다 — 흐름 제어를 따로 안 짜도 된다.

out_valid 가 take 보다 한 클럭 늦은 것은 출력이 레지스터이기 때문이다.

세 가지가 헷갈리기 쉽다

패딩에는 시간이 없다

실프레임 100개만 FRAME_CYCLES 를 기다린다. 앞뒤 패딩 14개씩은 악수가 되는 대로 곧바로 나간다 — 시간축에 대응되는 게 없으니 기다릴 이유가 없다. 실행기에서 S_PADL 이 순식간에 지나가고 그동안 fc 가 — 인 게 그래서다.

패딩은 −1 이지 0 이 아니다

모듈은 {0,1} 로 내보내고 아래쪽에서 0 → −1 로 매핑한다. 그래서 0 인 워드가 곧 전 채널 −1 이다. −1 은 빈칸이 아니라 "이 대역에 에너지가 없다"는 유효한 관측 이고, conv1 이 그 전제로 학습돼 있다. 중립값을 넣으면 학습한 적 없는 입력이 된다.

창이 닫혔는데 앞 프레임이 안 나갔다면

frame_edge && pending 이면 네트워크가 FRAME_CYCLES 안에 못 끝냈다는 뜻이다. 이 모듈의 잘못이 아니라 시스템의 실시간 위반이고, 안 잡으면 프레임이 조용히 덮인다. 그래서 KWS_ASSERT 가 여기서 죽는다.
