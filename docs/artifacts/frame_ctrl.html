kws_frame_ctrl 사이클 실행기

설계 전체에서 비동기 신호를 만지는 모듈은 이것 하나뿐이다. 왼쪽에는 클럭이 없는 비교기 16가닥이 있고, 오른쪽에는 완전히 동기화된 [16,128] 텐서가 있다. 그 사이를 플립플롭 50개 남짓이 잇는다. 한 클럭씩 밟아 보자.

리셋 상태다. 실행이나 클럭 1을 누르면 start 가 한 클럭 뜬다.
그림의 숫자는 줄여 놓았다. 여기서는 FRAME_CYCLES=6, NATIVE_T=10, PAD_LEFT=PAD_RIGHT=3, T=16 이다. 실제 값은 1,000,000 / 100 / 14 / 128 — 100 MHz 에서 10 ms 프레임이라 프레임 하나가 백만 클럭이고 눈으로 볼 수가 없다. rtl/tb/tb_frame_ctrl.v 도 같은 이유로 FRAME_CYCLES 를 줄여서 돌린다. 구조는 그대로다.

Verilog 한 줄이 그림에서 어디인가

네 덩어리뿐이다. 위 실행기에서 각 줄이 무엇을 움직이는지 대조해 보면 된다. 

(* ASYNC_REG = "TRUE" *) reg [15:0] sync1;
(* ASYNC_REG = "TRUE" *) reg [15:0] sync2;

always @(posedge clk or negedge rst_n)
  if (!rst_n) begin
    sync1 <= 0;  sync2 <= 0;
  end else begin
    sync1 <= cmp_in;
    sync2 <= sync1;
  end

1. 2단 동기화기

cmp 는 우리 클럭과 아무 관계가 없다. 클럭 에지 바로 그 순간에 값이 바뀌면 sync1 은 0 도 1 도 아닌 중간 전압에 걸릴 수 있다 (메타스테이빌리티). 한 클럭을 더 주면 그 사이 안정되고, sync2 는 깨끗한 값을 본다.

16채널이 한 줄인 이유: 반복문이 아니라 플립플롭 16개가 물리적으로 나란히 있는 것이다. 서로 기다리지 않는다.

always @(posedge clk or negedge rst_n)
  if (!rst_n || start) sticky <= 0;
  else if (frame_edge) sticky <= 0;
  else if (st == S_RUN) sticky <= sticky | sync2;

2. sticky OR — 이게 축약 규칙 그 자체다

CLAUDE.md 2.8 은 "창 안에서 한 번이라도 1 이면 1"(reduce = max) 이라고 정한다. {0,1} 위에서 max 는 정확히 OR 이다. 그래서 여기엔 근사가 없다 — 래치가 곧 규칙이다.

지우는 시점이 프레임 경계뿐이라는 게 핵심이다. 창 중간에 지우면 그 앞의 펄스가 사라진다.

wire frame_edge = (st == S_RUN) && (fc == FC_LAST);

S_RUN: begin
  fc <= (fc == FC_LAST) ? 0 : fc + 1;
  if (frame_edge) begin
    held    <= sticky | sync2;
    pending <= 1'b1;
  end
  ...
end

3. 프레임 타이머

fc 가 FRAME_CYCLES 를 세면 창이 닫힌다. 그때 sticky 를 held 로 퍼내고 pending 을 올린다.

sticky | sync2 인 이유: 경계 그 사이클도 닫히는 창에 속한다. sticky 만 쓰면 그 한 사이클을 잃고, 다음 창에 넣으면 두 번 세게 된다. 이렇게 하면 모든 사이클이 정확히 한 창에 들어간다.

wire take = pending && out_ready;

if (take) begin
  out_valid <= 1'b1;
  out_frame <= held;
  pending   <= 1'b0;
  cnt       <= cnt + 1;
end

4. 악수 (handshake)

pending 은 "내보낼 프레임이 있다", out_ready 는 "받을 수 있다". 둘 다 참인 사이클에만 프레임이 건네진다. 소비자가 바쁘면 저절로 기다린다 — 흐름 제어를 따로 안 짜도 된다.

위 실행기의 소비자 느리게 를 켜 보면 이게 어떻게 깨지는지 볼 수 있다.

세 가지가 헷갈리기 쉽다

패딩에는 시간이 없다

실프레임 100개만 FRAME_CYCLES 를 기다린다. 앞뒤 패딩 14개씩은 악수가 되는 대로 곧바로 나간다 — 시간축에 대응되는 게 없으니 기다릴 이유가 없다. 실행기에서 S_PADL 이 순식간에 지나가는 게 그래서다.

패딩은 −1 이지 0 이 아니다

모듈은 {0,1} 로 내보내고 아래쪽에서 0 → −1 로 매핑한다. 그래서 0 인 워드가 곧 전 채널 −1 이다. −1 은 빈칸이 아니라 "이 대역에 에너지가 없다"는 유효한 관측 이고, conv1 이 그 전제로 학습돼 있다. 중립값을 넣으면 학습한 적 없는 입력이 된다.

창이 닫혔는데 앞 프레임이 안 나갔다면

frame_edge && pending 이면 네트워크가 FRAME_CYCLES 안에 못 끝냈다는 뜻이다. 이 모듈의 잘못이 아니라 시스템의 실시간 위반이고, 안 잡으면 프레임이 조용히 덮인다. 그래서 KWS_ASSERT 가 여기서 죽는다.
