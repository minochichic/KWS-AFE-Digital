# 아날로그 쪽에 요청할 것 — 데이터 포맷 스펙

**요약**: 비교기 16채널의 **전이(transition) 타임스탬프 CSV** 한 클립, 그리고
그게 어느 wav 인지. 그게 전부다. 나머지 변환은 우리가 한다.

---

## 1. 경계는 비교기 16가닥이다

디지털 쪽은 끝났다. 12개 모듈, 12,004개 값이 골든 벡터와 일치
(`docs/WHITEPAPER.md`). 아날로그에서 넘어오는 것은 **비교기 16가닥과 프레임
타이밍뿐**이고, 그게 `rtl/kws_frame_ctrl.v` 가 받는 전부다.

아날로그가 바뀌면 바뀌는 것은 **가중치**지 RTL 이 아니다 (`docs/ICD.md` §6).
RTL 로 넘어오는 아날로그 파라미터는 `N_CH`, `CMP_INVERT`, `FRAME_CYCLES` 셋뿐이다.

## 2. 우리가 지금 실험에 쓰는 파일 — `input.hex` 하나

`rtl/tb/tb_top.v:149` 가 `$readmemh` 로 이거 하나만 읽는다.

```
rtl/gen/xl_g12/golden/input.hex      256줄 = 2클립 x 128프레임
```

실물 (clip 0 의 44~55번 프레임):

```
frame  hex       ch15 ........ ch0
   44  00000006  0000000000000110
   45  0000004c  0000000001001100
   46  000000ec  0000000011101100
   47  000002ec  0000001011101100
   50  000043fc  0100001111111100
   54  00007ffc  0111111111111100
```

### 레이아웃

| | |
|---|---|
| **한 줄** | 한 프레임 = **10 ms** |
| **한 줄의 값** | 32비트 hex 워드. **하위 16비트만** 사용, 상위 16비트는 0 |
| **비트 위치** | **bit c = 채널 c.** ch0 = 최하위 비트 = **166 Hz** (최저 주파수) |
| **클립당** | 128줄 |

클립당 128줄의 구성 (CLAUDE.md §2.8):

| 줄 | 내용 |
|---|---|
| 0–13 | 패딩. 전부 `00000000` |
| **14–113** | **실제 100 프레임 = 1초** |
| 114–127 | 패딩. 전부 `00000000` |

> 패딩은 중립값이 아니라 **−1**("이 대역에 에너지 없음")이고, 이진 인코딩에서
> −1 은 비트 0 이라 워드가 통째로 0 이 된다. conv1 이 그 −1 에 대해 학습됐다.

**따라서 동료에게 실질적으로 필요한 것은 클립당 `100 프레임 x 16채널` 비트다.**
패딩과 hex 포장은 우리가 붙인다.

## 3. 요청 포맷

### 부탁은 한 줄이다

> **비교기가 언제 올라가고 언제 내려갔는지**만 주면 된다.
> 파일이 크든 작든, 포맷이 뭐든 상관없다. **다만 10 ms 로 접지(fold) 말 것.**

아래는 그게 왜 그런지, 그리고 어떻게 적으면 편한지다.

### 3.1 접지 말아야 하는 이유 ← 이 절이 핵심이다

**접기(fold)** = 비교기의 연속 사각파를 **10 ms 당 1비트**로 뭉개는 것.
`[16, 128]` 이미지를 만들려면 누군가는 반드시 해야 하는 일이다.

문제는 **접는 방법이 하나가 아니라는 것**이다. 채널 하나의 30 ms 를 보자:

```
     0ms        10ms       20ms       30ms
     |----------|----------|----------|
     __###____##_______________###_______________________########

     1 이었던 구간: 1.2~2.0, 4.6~5.1, 13.4~14.0, 26.0~29.8 ms
```

이걸 10 ms 칸 세 개로 접으면:

| 접는 규칙 | 칸0 | 칸1 | 칸2 | 결과 |
|---|:-:|:-:|:-:|---|
| **한 번이라도 1이면 1** ← 우리 하드웨어 | 1 | 1 | 1 | **`111`** |
| 칸 끝에서의 값 | 0 | 0 | 0 | `000` |
| 칸 시작에서의 값 | 0 | 0 | 0 | `000` |
| 절반 이상 1이었나 | 0 | 0 | 0 | `000` |

**같은 물리 신호인데 답이 정반대다.**

우리 하드웨어(`rtl/kws_frame_ctrl.v`)가 쓰는 것은 첫 번째 규칙 하나뿐이다 —
sticky OR, 래치는 **프레임 경계에서만** 클리어된다 (CLAUDE.md §2.8 의 `reduce=max`).

그런데 동료가 "칸 끝의 값"으로 접어 보내면 우리는 **`000` 을 받아놓고 그게 원래
`111` 이어야 했다는 걸 알 방법이 없다.** 넷 다 그럴듯한 0/1 패턴이라 검증도 안 된다.
증상은 정확도가 조금 이상한 것뿐이고, 그건 원인이 백 가지다.

**접는 순간 되돌릴 수 없다.** 그래서 접기 전 것을 받고, 접는 것은 우리가 한다 —
`experiments/trace_to_frames.py` 가 RTL 과 **같은 규칙으로** 접는다.

### 3.2 적는 방법 — 둘 다 되고, 정보는 같다

전이만 적든 샘플마다 적든 **정보량은 같다.** 파일 크기만 다르다.

**(A) 샘플마다 한 줄** — SPICE 가 그냥 뱉는 것. **이대로 줘도 된다.**

```csv
time_s,ch0,ch1,...,ch15
0.0000000,0,0,...,0
0.0000002,0,0,...,0      <- 200 ns 마다, 값이 안 변해도 계속 적는다
```

1초 = 약 **500만 줄**.

**(B) 전이마다 한 줄** — 값이 *바뀐 순간*만.

```csv
channel,time_s,value
0,0.001234,1        <- ch0 이 여기서 0->1
0,0.001901,0        <- 여기서 1->0
3,0.002011,1
```

1초 = 약 **5천 줄**. 1000배 작다.

**(B) 는 (A) 의 요약이 아니라 같은 정보의 다른 표기다.** 전이 사이 구간은 값이
안 바뀌므로 완전히 복원된다 — `0.001234` 에 1이 됐고 `0.001901` 에 0이 됐으면
그 사이는 전부 1인 게 확실하다.

> **그러니 (B) 는 요구가 아니라 부탁이다.** (A) 로 줘도 우리가 (B) 로 바꿔서 쓴다.
> VCD 든 ngspice raw 든 채널별 파일이든 마찬가지다. 편한 대로 주면 된다.

### 3.3 (B) 로 줄 경우의 컬럼

| 컬럼 | |
|---|---|
| `channel` | 0..15 |
| `time_s` | 초. 상대 시간이어도 된다 (`t0` 는 §4 에서 맞춘다) |
| `value` | 0 또는 1. **첫 줄 이전에는 0 으로 가정한다** |

줄 순서는 상관없다 — 시간순이든 채널별 블록이든 똑같이 읽는다.

### 3.4 "우리도 같은 규칙으로 접었는데?" — 그럼 써도 되나

**된다.** 규칙이 정말 같다면 비트가 같고, `100 x 16` 을 그대로 받아 쓰면 된다.
문제는 그게 **맞는지 확인할 방법이 없다는 것**이지, 불가능하다는 게 아니다.

"한 번이라도 1이면 1" 이라는 문장에는 숨은 조건이 여섯 개 붙어 있다. 하나만
어긋나도 결과가 달라지고, 프레임만 봐서는 어느 것이 어긋났는지 알 수 없다:

| | 우리 쪽 |
|---|---|
| 칸 0 이 시작하는 시각 | `t0`. 정착 구간이 있으면 그만큼 밀린다 (§4-1) |
| 칸 폭 | 정확히 10.000 ms |
| 칸 개수 | 100 개 (앞뒤 패딩 14+14 는 우리가 붙인다) |
| 경계에 걸친 펄스 | 반열린 구간 `[시작, 끝)`. 칸 끝에 **정확히** 끝나는 run 은 다음 칸을 켜지 않는다 |
| 채널 순서 | ch0 = 166 Hz (최저) (§4-2) |
| 극성 | 1 = envelope > threshold (§4-3) |

### 그래서 이렇게 하면 된다 — 한 클립만 원본으로

> **첫 클립만 접기 전(원본)으로 같이 주고, 그 클립의 접은 결과도 같이 준다.**
> 우리가 원본을 우리 규칙으로 접어서 **그쪽 프레임과 비트 단위로 대조**한다.
> 일치하면 접는 규칙이 검증된 것이고, **그 뒤부터는 프레임만 줘도 된다.**

한 번만 맞춰 놓으면 그다음부터는 파일이 1000배 작아지고 동료도 편하다.

```bash
python -m experiments.trace_to_frames --trace cmp.csv --verify-frames theirs.txt
```

`theirs.txt` 는 **한 줄에 한 프레임**이면 되고, hex 워드(`00007ffc`)든 0/1 열
(`0111111111111100`, **왼쪽이 ch15**)이든 읽는다.

일치하면 그렇게 말해주고, 어긋나면 **위 표의 어느 줄이 원인인지 짚어준다**:

```
### 그쪽 t0 가 10 ms 늦은 경우
their frames vs ours, folded from the same trace: 5 of 1600 bits differ (0.31%)
  per channel: 0:5
  Shifting one frame drops it to 0: their grid is offset by
  a window. Fix --t0, not the circuit.

### 그쪽이 "칸 끝의 값"으로 접은 경우
  They light far fewer bits (2 vs 8): a fold that samples
  the window instead of OR-ing it -- the case ASK_ANALOG 3.1 draws.

### 채널 순서가 반대인 경우
  per channel: 0:8  15:8
  Reversing the channel order drops it to 0: ch0 is their highest
  frequency, not their lowest.
```

**전부 프레임으로만 받았다면 못 짚었을 것들이다.** 불일치 비트 수 하나만 보고는
t0 문제인지 회로 문제인지 구별할 방법이 없다.

## 4. 같이 정해야 할 것 — 이게 없으면 조용히 어긋난다

전부 한 줄짜리 답이면 된다.

### (1) `t0` — 트레이스의 몇 초가 프레임 0 인가

시뮬 앞에 정착(settling) 구간이 있으면 그만큼 밀린다. **오디오가 시작되는 시각**을
알려주면 된다. 없으면 0 으로 둔다.

### (2) 채널 순서

우리는 **ch0 = 166 Hz (최저), ch15 = 6761 Hz**.
반대로 매겼으면 전부 뒤집힌다 — 그리고 뒤집힌 스펙트럼도 그럴듯한 오답을 낸다.

### (3) 극성

`value=1` 이 **"envelope > threshold"** 인가, 아래인가.
반전이면 `CMP_INVERT` 파라미터 하나로 흡수한다. 재설계가 아니다.

### (4) 어느 wav 인가 ← **(1)~(3) 만큼 중요하다**

같은 오디오로 우리 소프트웨어 AFE 를 돌려야 **대조**가 된다.
`analog/AFE/audio/` 에 GSC 클립 12개가 이미 있다 (`go.wav` `no.wav` `yes.wav`
`up.wav` `down.wav` `left.wav` `off.wav` `on.wav` `stop.wav` `six.wav` `seven.wav`
`sheila.wav`). **여기서 하나 고르면 제일 깔끔하다** — 정답 레이블은 우리가 안다.

## 5. 받으면 우리가 하는 것

### 5.1 먼저 대조. 분류가 아니다

가중치는 **우리 소프트웨어 AFE 로 학습됐다.** 실물 회로의 거동이 다르면 ±1 패턴이
달라지고, 학습된 가중치는 그 패턴을 설명하지 못한다.
**그때 나오는 건 에러가 아니라 자신만만한 오답이다.**

```bash
python -m experiments.trace_to_frames --trace cmp.csv \
       --compare runs/xl_g12 --wav analog/AFE/audio/go.wav
```

같은 오디오에 대해 **우리 시뮬 vs 그쪽 회로**의 비교기 출력을 비트 단위로 센다.

| 불일치 | 뜻 | 다음 |
|---|---|---|
| ~0% | 우리 시뮬이 회로를 잘 맞췄다 | 그대로 분류. 정확도도 유지될 것 |
| 몇 % | 대체로 맞고 채널 몇 개가 어긋남 | 어긋난 채널만 조사 (threshold? f_c?) |
| 10% 이상 | **다른 프론트엔드다** | 회로에 맞춰 **재학습**. RTL 은 안 바뀐다 |

한 채널만 유난히 나쁘면 그 채널의 threshold 나 중심주파수가 움직인 것이지
프론트엔드 전체가 틀린 게 아니다 — 스크립트가 채널별로 찍는다.

### 5.2 그다음 RTL 로 클래스까지

`--vectors` 가 테스트벤치가 바로 먹는 디렉터리를 만든다 (`input.hex` +
기대 클래스 + `paths.vh`). **골든 벡터를 덮어쓰지 않는다.**

```bash
python -m experiments.trace_to_frames --trace cmp.csv --t0 0.0 \
       --compare runs/xl_g12 --wav analog/AFE/audio/go.wav \
       --vectors out/cmp_vectors
```

```bash
./rtl/run_tb.sh top xl_g12 out/cmp_vectors
```

세 번째 인자가 **자극(stimulus)만** 바꾼다. 가중치는 그대로 `xl_g12` 다.

> **여기서 mismatch 가 나면 그게 고장이 아니라 측정값이다.** 기대 클래스는
> "우리 파이프라인이 같은 오디오를 뭐라고 부르는가"이므로, 어긋났다는 것은
> **회로의 비트가 우리 시뮬의 비트와 다른 단어를 골랐다**는 뜻이다 — 트레이스를
> 받는 이유 그 자체다. 5.1 의 불일치율이 그 원인을 채널별로 짚어준다.

## 6. 몇 클립이 필요한가 — 기대치를 정확히

| 클립 수 | 얻는 것 |
|---|---|
| **1** | **비트 단위 대조.** 시작하기에 이걸로 충분하다 |
| ~12 | 채널별 불일치의 안정된 추정. 단어마다 쓰는 대역이 다르므로 |
| 수백 | 정확도. **SPICE 로는 현실적으로 불가능하다** |

**중요**: 트레이스 몇 개로 "정확도"는 안 나온다. 나오는 것은 **"우리 시뮬이 회로를
얼마나 잘 흉내내나"** 이고, 그게 답을 못 얻고 있던 유일한 질문이다. 정확도는
GSC 전체로 이미 측정돼 있다 (§7).

**그러니 한 클립부터 시작하면 된다.** 무리해서 여러 개 돌릴 필요 없다.

### 8.2 부품 공차 — 제작 확정 시

`analog/AFE/artifacts/component_table.md` 는 **연속 설계값**이고 첫 줄이 그렇게
적고 있다. 커패시터가 `76.56 / 42.35 / … / 1.86 nF` 라 실재하지 않는다.
스냅은 우리가 다시 풀 수 있다 (`RA → f_c`, `R1 → Q` 가 분리돼 있다). 공차는 못 고친다:

`f_c ∝ 1/(RA·C)` 라 커패시터가 지배하고, 우리 Q 는 1.3~6.5 로 좁다.
**f_c 가 ±10% 밀리면 ch15 에서는 그 채널 대역폭의 65%** 다 (ch0 은 13%).
우리 설계 오차 0.9% 보다 한 자릿수 크다.

→ 부품 확정 시 **커패시터 유전체 하나만 확인하면 된다**: C0G/NP0 면 f_c 총 이동이
±3~5% 로 괜찮고, X7R 이면 온도·DC 바이어스까지 ±25% 라 대역폭 1.5배를 넘는다.

**지금 물어볼 항목은 아니다** — 동료가 시뮬레이션으로 부품을 정하는 단계가 끝난 뒤,
확정된 값으로 `filterbank_matrix.csv` 를 재생성할 때 필요하다.
