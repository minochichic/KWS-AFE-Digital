## 🔴 1. (새 요청) 채널별 임계값을 바꿔주세요 — 이게 진짜 원인입니다

저희 시뮬은 같은 조건 10클래스에서 **0.826~0.841**, 전송본은 **0.70~0.73** 입니다.
모델 쪽은 다섯 가지를 바꿔봤는데 전부 1pp 안에서만 움직였습니다. 원인은
**임계값 배치**입니다.

### 근거 1 — 저희 최대 레버가 정확히 이것입니다

임계값이 어디 앉느냐만 바꿔서 **0.717 → 0.817 (+10pp)** 를 낸 기록이 있습니다.
지금 남은 격차가 정확히 그 크기입니다.

### 근거 2 — 전송본의 정보량이 1.9비트 적습니다

| | 채널 총 비트 | 평균 발화율 |
|---|---:|---:|
| 저희 시뮬 | **11.16 / 16** | 20.6% |
| 전송본 | 9.26 / 16 | 14.4% |

### 근거 3 — 임계값이 균일한데, 최적값은 균일하지 않습니다

현재 Vthr 는 세 단계뿐입니다 (검출기 정지점 938.10 mV 위 **31.9 / 41.9 / 51.9 mV**,
채널 간 1.6배 차이). 그런데 저희가 학습한 값은 **채널 간 60배** 차이가 납니다.
네트워크는 채널마다 아주 다른 동작점을 원합니다.

가장 심한 게 **ch15** 입니다:

| ch | 저희가 원하는 발화율 | 전송본 실제 | 배수 |
|---:|---:|---:|---:|
| **15** | **35.3%** | **1.9%** | **18.3×** |
| 13 | 29.1% | 10.5% | 2.8× |
| 10 | 33.5% | 13.1% | 2.6× |
| 2 | 36.4% | 18.2% | 2.0× |
| 0 | 7.8% | 11.7% | 0.7× |
| 4 | 10.2% | 17.9% | 0.6× |

**ch15 가 사실상 죽어 있습니다.** 저희 모델이 가장 많이 쓰는 채널 중 하나인데
100프레임 중 2프레임만 켜집니다. 저희가 SPICE 로 잰 "ch15 스윙이 가장 약함
(0.4 mV 입력에서 15.99 mV)" 과 균일한 31.9 mV 임계값이 겹친 결과입니다.

### 요청 형식: **전압이 아니라 발화율**

`docs/request_v4/target_firing_rates.csv` — `ch, f_c_hz, target_fire_pct,
current_fire_pct, ratio`.

전압으로 드리면 저희가 모르는 상수(정규화 1.0 이 몇 mV 인가)를 가정해야 합니다.
**발화율은 그 가정이 필요 없습니다** — 동료분 출력에서 직접 세면 되는 값이니까요.

채널마다 **Vthr 를 이분법으로 조정해서 그 채널의 전체 발화율이 목표치가 되게**
맞춰주시면 됩니다. 대체로 **지금보다 낮춰야** 합니다 (평균 14.4% → 20.6%).

그렇게 다시 뽑아주시면 임계값 가설이 맞는지 바로 확정됩니다.

## 2. 클립 원래 타이밍 버전 (가장 중요)

v3 는 `trigger: "first sample where any channel v_env >= vthr"` 로 첫 비교기
이벤트에 정렬합니다. **이건 wake-up 하드웨어에 충실한 설계이고 잘못이 아닙니다.**
다만 그것 때문에 정보가 앞 30프레임에 몰립니다 — 저희가 측정한 값입니다:

| 구간 | 선형 프로브 정확도 |
|---|---:|
| 전체 0-99 | 0.577 |
| **앞 0-29 만** | **0.567** |
| 뒤 40-99 | 0.136 (랜덤 0.10) |

프레임 60 이면 클립의 **96% 가 완전히 비어** 있습니다.

**요청**: 트리거 없이 **클립 t=0 에서 시작해 100 bin(1초)** 을 그대로 뜬 버전.

### "1초 넘는 것"에 대해

말씀하신 대로 회로 응답은 1초를 넘습니다 (C3 τ 가 최대 21.5 ms 라 단어가 끝난
뒤에도 v_env 가 감쇠하며 이어짐). **그건 그냥 자르시면 됩니다.**

저희 파이프라인이 이미 그렇게 합니다 — 원본 wav 를 `wave[:16000]` 으로 앞 1초만
쓰고, 짧으면 뒤를 0 으로 채웁니다. **1초 뒤의 꼬리는 저희 시뮬도 본 적이 없으므로**
버리는 게 손실이 아니라 오히려 **일치**입니다.

즉 규칙은 단순합니다:

- 시작 = 클립 t=0 (트리거 없음)
- 길이 = 100 bin 고정
- 100 bin 을 넘는 응답 = 버림
- 100 bin 이 안 되면 = 0 으로 채움

(참고로 Speech Commands v2 의 단어 wav 자체는 1초 이하입니다. 1초를 넘는 건
`_background_noise_` 뿐인데 그건 아래 2번에서 잘라 쓰는 용도입니다.)

## 2. `_silence_` 와 `_unknown_`

저희 과제는 12클래스입니다. v3 에는 키워드 10개뿐이라 나머지 둘이 없습니다.

| 클래스 | 만드는 법 | 저희 12클래스에서의 성적 |
|---|---|---|
| `_silence_` | `_background_noise_` 의 6개 파일에서 **1초씩 잘라내기** | 0.993 (최고) |
| `_unknown_` | 키워드 10개를 뺀 **나머지 25개 단어**에서 일부 | 0.644 (최악) |

이 둘이 정확히 저희 최고·최악 클래스라, 빼고 재면 숫자가 어느 쪽으로 움직일지
계산이 안 됩니다. **12클래스로 맞춰야 비교가 됩니다.**

### ⚠️ "아무거나 3,800개"로는 안 됩니다

어떤 클립을 고르느냐는 저희 쪽 시드가 정합니다. 동료가 다른 3,800개를 뽑으면
`_unknown_` 의 **구성이 달라져** 그 클래스 정확도를 비교할 수 없습니다. 그래서
**저희가 실제로 쓰는 목록을 뽑아서 드립니다.**

두 클래스는 성격이 다릅니다:

| | 어떻게 만들어지나 | 넘기는 형식 |
|---|---|---|
| `_unknown_` | 25개 단어에서 **골라낸 것** | **파일명 목록** (`unknown_list.csv`) |
| `_silence_` | 배경잡음에서 **잘라 만든 것** | **(파일, 시작샘플, 길이)** (`silence_crops.csv`) |

`_silence_` 는 파일명만으로는 부족합니다 — 같은 잡음 파일의 어디를 1초 잘랐는지가
클립을 정합니다. 그래서 크롭 위치까지 드립니다.

개수는 대략 이렇습니다 (키워드 개수의 10%씩):

| split | 키워드 (이미 있음) | `_unknown_` | `_silence_` |
|---|---:|---:|---:|
| train | 30,769 | ~3,077 | ~3,077 |
| val | 3,703 | ~370 | ~370 |
| test | 4,074 | ~407 | ~407 |
| **합** | 38,546 | **~3,854** | **~3,854** |

**추가로 돌리실 건 약 7,700개**입니다 (25개 단어 전체 66,000개가 아닙니다).

## 3. draft → 검증본

`export_settings.json` 에 도구 자신의 경고가 있습니다:

```
"status": "draft"
"draft package: 일부 채널 또는 Vthr band의 일치가 보장되지 않습니다."
"보장 Vthr band 없음: ch00, ch01, ..., ch15"      ← 16채널 전부
```

가능하면 검증된 패키지로 부탁드립니다. 임계값이 임의값인 것과는 별개로, 도구가
**어느 채널도 보장 못 한다**고 말하고 있어서 숫자를 어디까지 믿을지 판단이 안
섭니다.

## 우선순위

1. **채널별 임계값 조정** (`target_firing_rates.csv`) — 유일하게 남은 가설이고,
   저희 최대 레버와 크기가 같습니다.
2. `_unknown_` + `_silence_` (`unknown_list.csv`, `silence_crops.csv`) —
   12클래스 비교와 **오탐율** 측정에 필요합니다. 지금은 키워드 아닌 클립이 없어서
   오탐율을 아예 잴 수 없습니다.
3. draft → 검증본.

1번이 압도적으로 큽니다. 시간 정렬은 이미 배제됐고, 클래스 수도 저희가 재집계로
배제했습니다. **남은 건 임계값 하나입니다.**

### 참고: 측정으로 배제한 것들

저희가 학습한 가중치에 전송본을 **그대로 넣어봤습니다** (재학습 없음):

| | 정확도 |
|---|---:|
| 그대로 | **0.41** |
| 채널 순서를 뒤집으면 | 0.14 (랜덤 0.10) |
| 시간축을 ±20프레임 밀면 | 0.37~0.41 (평평) |

- 채널 뒤집기가 무너지므로 **채널 순서는 지금이 맞습니다**.
- 시프트가 평평하므로 **시간축도 안 어긋나 있습니다** (어긋났으면 봉우리가 나옴).
- 0.41 은 랜덤(0.10)보다 훨씬 높고 저희 자체 데이터(0.83)보다 훨씬 낮습니다 —
  **같은 소리에 다른 비트 패턴**이 나온다는 뜻이고, 임계값 차이의 모습입니다.

## 참고: v3 에서 저희가 찾은 것들

받은 데이터 자체는 **정상**입니다. 죽은 채널 0개, 포화 0개, 발화율 4~24%.
아래는 저희가 맞춰야 했던 것들이라 공유합니다.

- **`row_order` 가 역순**입니다 (`[ch15 ... ch00]`, CSV 행 0 = 최고역). 매니페스트에
  적혀 있어서 읽어서 처리했습니다. 의도하신 거면 그대로 두셔도 됩니다.
- 채널 총 비트 **9.05 / 16** (저희 시뮬은 11.16).
- 저희가 SPICE 로 잰 "고역 스윙이 약하다"와 데이터가 일치합니다 — 되돌린 순서로
  ch0(최저역) 10%, ch15(최고역) 2% 발화.
