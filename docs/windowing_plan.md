# 계획 — `start` 를 누가 언제 올릴 것인가

그림: [언제 추론할 것인가](https://claude.ai/code/artifact/ce567cb9-6a1c-46b6-aadc-03b3c8e45583)
(생성기 `docs/artifacts/gen_windowing.py`)

이 문서는 **계획만** 담는다. 여기에 적힌 어떤 것도 아직 구현되지 않았다.

---

## 0. 지금 막혀 있는 것

`start` 는 확장 포트의 핀 하나이고 DIP 스위치를 가정한다(`rtl/kws_board_top.v`).
보드에서는 아무도 누르지 않는다. 비교기는 쉬지 않고 들어오는데 **언제 1초를 잘라
신경망에 넣을지가 없다.**

### 결정적 사실 — 포착이 `start` 에 묶여 있다

`rtl/kws_frame_ctrl.v` 의 sticky OR:

```verilog
if (!rst_n || start)     sticky <= 0;
else if (frame_edge)     sticky <= 0;
else if (st == S_RUN)    sticky <= sticky | sync2;   // ← S_RUN 에서만
```

`S_IDLE` 에서는 비교기를 **아예 보지 않는다.** 그래서 "늘 최근 1초를 들고 있는
버퍼" 는 지금 구조 위에 그냥 얹을 수 없다. 포착이 먼저 풀려야 한다.

이것이 이 계획의 첫 갈림길이고, 나머지는 여기서 따라 나온다.

---

## 1. 결정 — 포착을 어떻게 늘 돌릴 것인가

| | 방법 | RTL 변경 | 위험 |
|---|---|---|---|
| **A** | `kws_frame_ctrl` 을 고쳐 포착을 자유 실행으로 | 검증된 모듈 3줄 | `tb_frame_ctrl` 이 시퀀싱을 검사하므로 깨질 수 있다 |
| **B** | `kws_window` 가 포착을 **자체 구현** | 새 모듈만 | **ICD §5 경계가 두 벌**이 된다 — 가장 틀리면 안 되는 15줄을 복제 |
| **C** | 파라미터로 자유 실행 (`NATIVE_T` 를 거대하게) | 0 줄 | `NATIVE_T = 16777215` 인 `kws_frame_ctrl` 은 이름과 주석이 거짓말을 한다 |
| **D** ★ | 포착을 `kws_capture` 로 **추출**하고 둘이 공유 | 기계적 분리 | 낮다 — 아래 |

### 권하는 것: D

```
kws_capture      2FF 동기화 + sticky OR + 프레임 타이머      ← ICD §5, 한 벌만 존재
  ├─ kws_frame_ctrl  (enable = st==S_RUN)   기존 동작 그대로
  └─ kws_window      (enable = 1)           늘 돈다
```

**추출이 충실했는지는 공짜로 확인된다.** `tb_frame_ctrl` 은 16가닥을 각자 다른
오프셋에서 한 사이클씩 흔들어 놓고 출력이 `<gen>/golden/input.hex` 와 **비트 일치**
하는지 본다 — 패딩·프레이밍·이산화 규칙을 한꺼번에. 그 테스트가 **고치지 않은 채로**
통과하면 분리가 맞은 것이다.

B 를 버리는 이유가 이것과 같다. 경계 로직이 두 벌이면 둘 중 하나만 고쳐지는 날이
오고, 그 증상은 "정확도가 좀 낮다" 뿐이다.

C 는 돌긴 하겠지만 `FRAME_CYCLES`·`NATIVE_T`·`T` 가 이름과 다른 뜻이 된다. 이
프로젝트의 규율이 "이름과 주석이 근거를 나른다" 인데 그걸 정면으로 깬다.

## 2. 단계

### 단계 1 — 자동 반복으로 보드에서 일단 돌린다

`kws_board_top.v` 에서 `start` 를 `~busy` 로 묶는다. **RTL 추가 0.**

겹치지 않는 창이라 경계에 걸린 단어는 놓친다. 그래도 이 단계가 답하는 질문이 있다:
**비트스트림이 올라가고, 비교기가 실제로 프레임이 되고, 분류 결과가 핀에 나오는가.**
그게 확인되기 전에 창 설계를 얹으면 실패했을 때 원인이 둘로 갈린다.

- 검증: `tb_board_top` 을 2회 연속 추론으로 확장. 보드에서는 말하면서 `class_idx` 가
  바뀌는지.
- 끝나는 조건: 보드에서 키워드 하나가 한 번이라도 맞으면.

### 단계 2 — `kws_capture` 추출

| | |
|---|---|
| 만드는 것 | `rtl/kws_capture.v` — 2FF + sticky OR + 프레임 타이머, `enable` 입력 |
| 고치는 것 | `kws_frame_ctrl` 이 그것을 인스턴스화 (`enable = st==S_RUN`) |
| **검증** | **`./rtl/run_tb.sh frame_ctrl` 이 수정 없이 통과** |

테스트벤치를 한 줄도 안 고치고 통과해야 한다. 고쳐야 한다면 분리가 틀린 것이다.

### 단계 3 — `kws_window`

```
kws_window #(N_CH=16, NATIVE_T=100, PAD_LEFT=14, PAD_RIGHT=14,
             FRAME_CYCLES=500000, TRIGGER_FRAMES=20)   // 20 프레임 = 200 ms = 5 Hz
  clk, rst_n, cmp[15:0], force_start
  out_valid, out_frame, out_ready, busy, overrun_count[7:0]
```

속: `kws_capture` + 원형 RAM(100 × 16 = **1,600 비트**) + 재생 FSM(PADL → 버퍼
100 → PADR) + 트리거 카운터.

**핵심 한 줄**: 트리거 시각의 쓰기 포인터를 스냅샷해 거기서부터 읽는다. 재생이
22배 빠르므로(0.45 ms/프레임 대 10 ms/프레임) 쓰기가 4.5칸 갈 동안 읽기가 100칸을
끝낸다 — 추월당하지 않는다.

**검증이 이 계획에서 가장 값싼 부분이다.** 새 골든 벡터가 필요 없다:

1. **스트림 등가** — `TRIGGER_FRAMES` 를 크게 잡고 `force_start` 로 한 번만 쏘면,
   `kws_window` 의 출력은 `kws_frame_ctrl` 의 출력과 **같아야 한다.** 같은
   `input.hex` 를 기대값으로 쓸 수 있다. 즉 `tb_frame_ctrl` 의 오라클을 그대로 재사용.
2. **순서·랩어라운드** — 프레임에 세는 패턴을 넣어(프레임 k = k) 재생 순서가
   오래된 것부터인지, 포인터가 100 에서 되돌 때 어긋나지 않는지. 어긋나면 눈에 띈다.
3. **overrun** — 일부러 주기를 57.4 ms 아래로 낮춰 트리거가 busy 중에 오게 하고,
   카운터가 오르고 **출력이 깨지지 않는지**.

> 새 골든 벡터가 필요 없다는 것이 중요하다. 골든 벡터를 뽑으려면 torch 와 학습
> 박스가 필요한데, 스트림 등가는 시뮬레이터만으로 확인된다. 아래층(`kws_top`)은
> 안 건드리므로 이미 검증된 것이 그대로 유효하다.

### 단계 4 — 투표 평활

`rtl/kws_vote.v` — `class_idx` 를 받아 같은 비-silence 클래스가 N회 연속이면
검출 선언, 이후 락아웃. `kws_top` 은 안 건드린다.

- 검증: 순수 시퀀스 로직이라 테스트벤치가 짧다. 입력 열 → 기대 출력 열.
- N 과 락아웃 길이는 **보드에서 재보고 정한다.** 미리 못 정한다.

### 단계 5 — `start` 핀을 override 로 정리

자동 트리거와 OR 하되 `busy` 로 게이트한다:

```
trig = (auto_tick | force_pulse) & ~busy
```

브링업과 XSim 테스트벤치가 수동 경로를 쓴다. 자동화가 들어와도 **그 경로를 없애면
안 된다** — 보드에서 한 발만 쏴보는 능력은 디버깅의 기본이다.

## 3. 왜 이 방안인가

1. **검증된 두 모듈을 안 건드린다.** `kws_top`(12모듈 골든 검증)과 아날로그 경계
   (ICD §5)는 그대로다. 위험이 새 모듈 하나에 갇힌다.

2. **신경망이 보는 입력이 학습과 비트 단위로 같다.** `−1` 14개 + 실제 100개 +
   `−1` 14개. 패딩 `−1` 은 중립값이 아니라 **학습된 관측**이고(CLAUDE.md §2.8),
   그것을 그대로 유지하는 것이 재학습·가중치 변경·ICD 변경을 전부 0으로 만든다.

3. **등가로 검증한다.** 새 골든 벡터가 필요 없고, 따라서 학습 박스가 필요 없다.
   `tb_frame_ctrl` 의 `input.hex` 오라클을 두 번 재사용한다(단계 2, 단계 3).

4. **원래 독립인 두 속도를 분리한다.** 포착 속도는 아날로그가 정한다(sticky OR
   창 = CLAUDE.md §2.8 의 이산화 규칙). 추론 속도는 제품 결정이다. 지금은 둘이
   묶여 있어 한쪽을 바꾸면 다른 쪽이 끌려간다.

5. **22배 여유가 어려운 부분을 없앤다.** 더블버퍼도, 중재도, 스냅샷 복사도
   필요 없다. 그 여유는 conv1 처리량에서 나오고 **측정값**이지 가정이 아니다
   (`tb_top` 의 2.87 M 사이클).

6. **경계 놓침을 고치는 가장 작은 것이다.** VAD 트리거도, 겹치는 추론 파이프라인도
   더 크고, 우리에게 없는 문제를 푼다.

## 4. 고려하고 버린 것

| 안 | 왜 버렸나 |
|---|---|
| **겹치지 않는 자동 반복만** | 단계 1 로 남긴다. 경계에 걸린 단어를 놓치는 것이 설계 결함이지 튜닝 문제가 아니다 |
| **VAD / 에너지 트리거** | 모델에 silence 클래스가 있어 조용한 창은 이미 처리된다. FPGA 는 콘센트를 꽂고 쓴다. 그리고 **튜닝할 문턱이 하나 생긴다** — ICD 가 없애려던 바로 그 종류 |
| **원형 버퍼 더블버퍼링** | RAM 이 3,200 비트로 늘 뿐 싸다. 다만 22배 여유가 측정값이라 지금은 불필요. **클럭을 낮추게 되면 이쪽으로 간다** |
| **증분/스트리밍 추론** (겹치는 창끼리 연산 재사용) | 훨씬 효율적이지만 conv1 과 파이프라인 전체를 다시 짜야 한다. 57.4 ms / 200 ms 에서 그럴 이유가 없다 |

## 5. 열린 질문

| # | 질문 | 왜 지금 못 정하나 |
|---|---|---|
| 1 | **2.87 M 사이클이 입력과 무관하게 일정한가** | 데이터 의존 분기가 없어 보이지만 **확인한 적 없다.** 일정하면 10 Hz 의 1.7배도 안전하고, 아니면 5 Hz 가 맞다 |
| 2 | 트리거 주기 5 Hz vs 10 Hz | 1번에 달렸다. **5 Hz 로 시작**하기를 권한다 — 여유 3.5배, 1초 단어를 200 ms 간격으로 훑어도 안 놓친다 |
| 3 | 투표 깊이 N 과 락아웃 길이 | 보드에서 오검출률을 봐야 정해진다 |
| 4 | `overrun` 을 어디에 보여줄 것인가 | LED 핀표가 아직 없다. 없으면 확장 포트로 뺀다 |
| 5 | 단계 1 에서 `class_idx` 를 어떻게 볼 것인가 | 지금 확장 포트 핀으로 나간다. LED 핀표가 오면 그쪽이 훨씬 낫다 |

> 1번은 `tb_top` 을 다른 클립으로 두어 번 더 돌려 사이클 수를 비교하면 끝난다.
> 단계 2 를 시작하기 전에 해 두면 2번이 자동으로 정해진다.

## 6. 로드맵 위치

`docs/ROADMAP.md` 의 P5 계열에서 **P5-g(합성·타이밍·보드) 뒤**에 온다.
P5-g 는 "보드에서 돈다" 이고 이 계획은 "보드에서 **쓸모 있게** 돈다" 다.

단계 1 은 P5-g 의 일부로 봐도 된다 — 그것 없이는 보드에서 아무 일도 안 일어난다.
