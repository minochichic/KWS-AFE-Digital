# 계획 — 언제 추론하고, 언제 그 답을 믿을 것인가

그림: [언제 추론할 것인가](https://claude.ai/code/artifact/ce567cb9-6a1c-46b6-aadc-03b3c8e45583)
(생성기 `docs/artifacts/gen_windowing.py`)

**이 문서는 계획만 담는다. 여기 적힌 것 중 구현된 것은 없다.**

| 결정 | 값 |
|---|---|
| 추론 주기 | **10 Hz** (프레임 10개마다) |
| 투표 깊이 | **N = 3** 연속 |
| 창 폭 | 1.28 s (`−1` 14 + 실제 100 + `−1` 14) |
| 연산 예산 | 57.4 ms / 100 ms = **여유 1.7배** |

---

## 0. 요점 — 이건 "start 를 언제 누를까" 문제가 아니다

**포착과 추론이 한 모듈에 잘못 묶여 있는 것**이 문제다.

비교기는 10 ms 마다 프레임을 만들고 신경망은 0.45 ms 마다 받을 수 있다. **22배 다른
속도인데 지금은 같은 FSM 이 둘 다 정한다.** 그래서 "1초를 잘라 넣는 시점" 이
"프레임을 모으는 시점" 과 붙어 버렸고, 창을 밀 자유가 없다.

그래서 답은 시작 시점을 **알아내는** 것이 아니다. **판단을 입력에서 출력으로 옮긴다**:

```
알아내려던 것   "지금이 단어의 시작인가"      -> VAD·온셋 검출기가 필요. 튜닝할 문턱이 하나 더 생긴다
대신 하는 것    계속 돌리고, 답이 안정되면 믿는다   -> 시작 시점 문제가 풀리는 게 아니라 없어진다
```

VAD 를 버리는 이유가 성능이 아니라는 점이 중요하다. **문턱이 하나 더 생기는 것**이
문제이고, 그건 `docs/ICD.md` 가 없애려던 바로 그 종류다.

### 이게 성립하는 진짜 이유: 12 클래스

모델에 **`silence` 와 `unknown` 클래스가 있다.** 조용한 창과 어긋난 창이 쓰레기를
내는 것이 아니라 `silence`/`unknown` 을 내고, 투표가 그것을 자연히 무시한다.

키워드 10개만 있었으면 모든 창이 억지로 키워드 하나를 골라야 해서 투표가 잡음이
됐을 것이다. **12 클래스 설계가 "그냥 계속 돌린다" 를 성립시킨다.**

### 슬라이딩과 투표는 한 쌍이다

둘 중 하나만으로는 안 된다.

- 슬라이딩 없이 투표만 → 1.28 s 에 답 하나. 900 ms 단어를 온전히 담는 창이
  **보장 0개 · 최대 1개**라(§1 의 식에 `P = 1280` 을 넣으면 나온다)
  **3연속이 원리적으로 불가능**하다.
- 투표 없이 슬라이딩만 → 초당 답 10개가 그대로 나와 LED 가 100 ms 마다 바뀐다.

**슬라이딩이 표를 만들고 투표가 그 표를 읽는다.**

## 1. 주기와 투표 깊이는 독립이 아니다 — 10 Hz + N=3 의 근거

폭 `W` = 1280 ms 인 창이 길이 `L` 인 발화를 **온전히** 담으려면 창 시작점이
`S = W − L` 폭 안에 들어와야 한다. 주기 `P` 로 밀면 그 구간에 들어가는 창 시작점의
개수는 격자 위상에 따라 `⌊S/P⌋` 또는 `⌊S/P⌋ + 1` 이다.

격자점 개수는 위상에 따라 하나 달라지므로 **보장값(`⌊S/P⌋`)** 으로 센다.
설계 근거로 쓸 수 있는 것은 최선의 경우가 아니라 보장되는 쪽이다.

| 발화 길이 `L` | `S = W−L` | **10 Hz** 보장 / 최대 | 5 Hz 보장 / 최대 |
|---|---|---|---|
| 400 ms | 880 ms | **8** / 9 | 4 / 5 |
| 600 ms | 680 ms | **6** / 7 | 3 / 4 |
| 800 ms | 480 ms | **4** / 5 | 2 / 3 |
| 900 ms | 380 ms | **3** / 4 | 1 / 2 |
| 980 ms | 300 ms | **3** / 4 ← 한계 | 1 / 2 |
| 1080 ms | 200 ms | 2 / 3 | 1 / 2 |

**N=3 이 보장되는 조건: `L ≤ 980 ms`** (10 Hz). GSC 는 1초 클립이고 그 안의 실제
발화가 보통 400~800 ms 이므로 보장 개수가 4~6개로 넉넉하다.

5 Hz 에서 같은 조건은 **`L ≤ 680 ms`** 로, 짧은 단어만 된다. **앞선 초안에서
"5 Hz 로 시작하는 편이 안전하다" 고 적었는데 틀렸다** — 연산 여유만 보고 표가
모이는지를 안 봤다. 5 Hz 를 고르려면 N=2 로 내려야 하고 그건 증거가 얇다.

> 이 표는 **하한**이다. 단어를 90% 만 담은 창도 맞히는 일이 흔하고(학습 클립도 단어가
> 늘 가운데 있지 않다), 그러면 실제 표는 더 모인다. 다만 그건 재봐야 아는 것이라
> 설계 근거로는 못 쓴다. **N 의 최종값은 보드에서 오검출률을 보고 정한다.**

### 10 Hz 를 고르면 생기는 부담

연산 여유가 1.7배뿐이다(5 Hz 면 3.5배). 그래서 **§5 의 1번(사이클 수가 입력과
무관하게 일정한가)이 있으면 좋은 확인이 아니라 선행 조건이 된다.**

## 2. 갈림길 — 포착이 `start` 에 묶여 있다

`rtl/kws_frame_ctrl.v` 의 sticky OR:

```verilog
if (!rst_n || start)     sticky <= 0;
else if (frame_edge)     sticky <= 0;
else if (st == S_RUN)    sticky <= sticky | sync2;   // ← S_RUN 에서만
```

`S_IDLE` 에서는 비교기를 **아예 보지 않는다.** "늘 최근 1초를 들고 있는 버퍼" 를
지금 구조 위에 그냥 얹을 수 없다.

| | 방법 | RTL 변경 | 위험 |
|---|---|---|---|
| A | `kws_frame_ctrl` 을 고쳐 포착을 자유 실행으로 | 검증된 모듈 3줄 | `tb_frame_ctrl` 이 시퀀싱을 검사하므로 깨질 수 있다 |
| B | `kws_window` 가 포착을 자체 구현 | 새 모듈만 | **ICD §5 경계가 두 벌**이 된다 — 가장 틀리면 안 되는 15줄을 복제 |
| C | 파라미터로 자유 실행 (`NATIVE_T` 를 거대하게) | 0 줄 | `NATIVE_T = 16777215` 인 `kws_frame_ctrl` 은 이름과 주석이 거짓말을 한다 |
| **D** ★ | 포착을 `kws_capture` 로 **추출**해 둘이 공유 | 기계적 분리 | 낮다 |

### 권하는 것: D

```
kws_capture      2FF 동기화 + sticky OR + 프레임 타이머      ← ICD §5, 한 벌만 존재
  ├─ kws_frame_ctrl  (enable = st==S_RUN)   기존 동작 그대로
  └─ kws_window      (enable = 1)           늘 돈다
```

**고른 이유는 설계가 예뻐서가 아니라 검증이 공짜라서다.** `tb_frame_ctrl` 은 16가닥을
각자 다른 오프셋에서 한 사이클씩 흔들어 놓고 출력이 `<gen>/golden/input.hex` 와
**비트 일치**하는지 본다 — 패딩·프레이밍·이산화 규칙을 한꺼번에. 그 테스트가
**고치지 않은 채로** 통과하면 분리가 맞은 것이다.

B 를 버리는 이유도 같다. 경계 로직이 두 벌이면 둘 중 하나만 고쳐지는 날이 오고,
그 증상은 "정확도가 좀 낮다" 뿐이다.

## 3. 단계

### 단계 0 — 사이클 수를 잰다 (선행)

`tb_top` 을 서로 다른 클립으로 두어 번 더 돌려 사이클 수를 비교한다. 데이터 의존
분기가 없어 보이므로 일정할 것으로 보지만 **확인한 적이 없다.**

- 일정하다 → 10 Hz 의 1.7배 여유가 안전하다. 계획대로 간다.
- 흔들린다 → 최악값으로 다시 계산한다. 주기를 늘리면 N 을 내려야 하므로 §1 표로
  돌아온다.

학습도 보드도 필요 없다. **여기서 시작하는 것이 맞다.**

### 단계 1 — 자동 반복으로 보드에서 일단 돌린다

`kws_board_top.v` 에서 `start` 를 `~busy` 로 묶는다. **RTL 추가 0.**

겹치지 않는 창이라 경계에 걸린 단어는 놓친다. 그래도 이 단계가 답하는 질문이 있다:
**비트스트림이 올라가고, 비교기가 실제로 프레임이 되고, 분류 결과가 핀에 나오는가.**
그게 확인되기 전에 창 설계를 얹으면 실패했을 때 원인이 둘로 갈린다.

- 검증: `tb_board_top` 을 2회 연속 추론으로 확장. 보드에서는 말하면서 `class_idx` 가
  바뀌는지.
- 끝나는 조건: 보드에서 키워드 하나가 한 번이라도 맞으면.

### 단계 2 — `kws_capture` 추출

| | |
|---|---|
| 만드는 것 | `rtl/kws_capture.v` — 2FF + sticky OR + 프레임 타이머, `enable` 입력 |
| 고치는 것 | `kws_frame_ctrl` 이 그것을 인스턴스화 (`enable = st==S_RUN`) |
| **검증** | **`./rtl/run_tb.sh frame_ctrl` 이 수정 없이 통과** |

테스트벤치를 한 줄도 안 고치고 통과해야 한다. 고쳐야 한다면 분리가 틀린 것이다.

### 단계 3 — `kws_window`

```
kws_window #(N_CH=16, NATIVE_T=100, PAD_LEFT=14, PAD_RIGHT=14,
             FRAME_CYCLES=500000,
             TRIGGER_FRAMES=10)        // 10 프레임 = 100 ms = 10 Hz
  clk, rst_n, cmp[15:0], force_start
  out_valid, out_frame, out_ready, busy, overrun_count[7:0]
```

속: `kws_capture` + 원형 RAM(100 × 16 = **1,600 비트**) + 재생 FSM(PADL → 버퍼
100 → PADR) + 트리거 카운터.

**핵심 한 줄**: 트리거 시각의 쓰기 포인터를 스냅샷해 거기서부터 읽는다. 재생이
22배 빠르므로(0.45 ms/프레임 대 10 ms/프레임) 쓰기가 4.5칸 갈 동안 읽기가 100칸을
끝낸다 — 추월당하지 않는다.

**검증이 이 계획에서 가장 값싼 부분이다.** 새 골든 벡터가 필요 없다:

1. **스트림 등가** — `TRIGGER_FRAMES` 를 크게 잡고 `force_start` 로 한 번만 쏘면
   `kws_window` 의 출력이 `kws_frame_ctrl` 의 것과 **같아야 한다.** 같은
   `input.hex` 를 기대값으로 쓴다. `tb_frame_ctrl` 의 오라클을 그대로 재사용.
2. **순서·랩어라운드** — 프레임에 세는 패턴을 넣어(프레임 k = k) 재생 순서가
   오래된 것부터인지, 포인터가 100 에서 되돌 때 어긋나지 않는지.
3. **overrun** — 주기를 일부러 57.4 ms 아래로 낮춰 트리거가 busy 중에 오게 하고,
   카운터가 오르고 **출력이 깨지지 않는지**. 10 Hz 는 여유가 1.7배뿐이라 이 경로가
   실제로 밟힐 수 있다. **건너뛰고 세는 것**이 규칙이다 — 조용히 버리면 현장에서
   예산 초과를 영영 모른다.

> 새 골든 벡터가 필요 없다는 것이 중요하다. 뽑으려면 torch 와 학습 박스가 필요한데,
> 스트림 등가는 시뮬레이터만으로 확인된다. 아래층(`kws_top`)은 안 건드리므로 이미
> 검증된 것이 그대로 유효하다.

### 단계 4 — 투표 평활 (`N = 3`)

`rtl/kws_vote.v` — `class_valid`/`class_idx` 를 받아 **같은 비-`silence`·비-`unknown`
클래스가 3회 연속**이면 검출을 선언하고, 이후 락아웃 동안 다시 선언하지 않는다.

```
sil sil sil unk yes yes unk yes yes yes yes unk sil ...
                                  └──3연속──┘ → 검출, 이후 락아웃
```

- 락아웃 길이 초기값: **1초**(트리거 10개). 한 발화가 두 번 세어지는 것을 막는
  것이 목적이다.
- `kws_top` 은 안 건드린다.
- 검증: 순수 시퀀스 로직이라 테스트벤치가 짧다. 입력 열 → 기대 출력 열.
- **N 과 락아웃은 보드에서 오검출률을 보고 다시 정한다.** §1 의 표는 N=3 이
  원리적으로 가능하다는 것만 말하지, 그게 최선이라는 말이 아니다.

### 단계 5 — `start` 핀을 override 로 정리

자동 트리거와 OR 하되 `busy` 로 게이트한다:

```
trig = (auto_tick | force_pulse) & ~busy
```

브링업과 XSim 테스트벤치가 수동 경로를 쓴다. 자동화가 들어와도 **그 경로를 없애면
안 된다** — 보드에서 한 발만 쏴보는 능력은 디버깅의 기본이다.

## 4. 왜 이 방안인가

1. **검증된 두 모듈을 안 건드린다.** `kws_top`(12모듈 골든 검증)과 아날로그 경계
   (ICD §5)는 그대로다. 위험이 새 모듈 하나에 갇힌다.

2. **신경망이 보는 입력이 학습과 비트 단위로 같다.** `−1` 14개 + 실제 100개 +
   `−1` 14개. 패딩 `−1` 은 중립값이 아니라 **학습된 관측**이고(CLAUDE.md §2.8),
   그것을 그대로 유지하는 것이 재학습·가중치 변경·ICD 변경을 전부 0으로 만든다.

3. **등가로 검증한다.** 새 골든 벡터가 필요 없고, 따라서 학습 박스가 필요 없다.
   `input.hex` 오라클을 두 번 재사용한다(단계 2, 단계 3).

4. **원래 독립인 두 속도를 분리한다.** 포착 속도는 아날로그가 정하고(sticky OR 창
   = CLAUDE.md §2.8 의 이산화 규칙) 추론 속도는 제품 결정이다. 지금은 묶여 있어
   한쪽을 바꾸면 다른 쪽이 끌려간다.

5. **22배 여유가 어려운 부분을 없앤다.** 더블버퍼도 중재도 스냅샷 복사도 필요 없다.
   그 여유는 conv1 처리량에서 나오고 **측정값**이지 가정이 아니다.

6. **경계 놓침을 고치는 가장 작은 것이다.** VAD 트리거도 겹치는 추론 파이프라인도
   더 크고, 우리에게 없는 문제를 푼다.

## 5. 고려하고 버린 것

| 안 | 왜 버렸나 |
|---|---|
| **겹치지 않는 자동 반복만** | 단계 1 로 남긴다. 경계에 걸린 단어를 놓치는 것은 설계 결함이지 튜닝 문제가 아니다 |
| **VAD / 에너지 트리거** | `silence` 클래스가 조용한 창을 이미 처리한다. FPGA 는 콘센트를 꽂고 쓴다. 그리고 **튜닝할 문턱이 하나 생긴다** — ICD 가 없애려던 그 종류 |
| **5 Hz 트리거** | 연산 여유는 3.5배로 좋지만 **표가 안 모인다**(§1) — N=3 보장이 `L ≤ 680 ms` 라 짧은 단어만 된다. N=2 로 내려야 하고 증거가 얇다 |
| **원형 버퍼 더블버퍼링** | RAM 이 3,200 비트로 늘 뿐 싸다. 다만 22배 여유가 측정값이라 지금은 불필요. **클럭을 낮추게 되면 이쪽으로 간다** |
| **증분/스트리밍 추론** (겹치는 창끼리 연산 재사용) | 훨씬 효율적이지만 conv1 과 파이프라인 전체를 다시 짜야 한다. 57.4 ms / 100 ms 에서 그럴 이유가 없다 |

## 7. 로드맵 위치

`docs/ROADMAP.md` 의 P5 계열에서 **P5-g(합성·타이밍·보드) 뒤**에 온다.
P5-g 는 "보드에서 돈다" 이고 이 계획은 "보드에서 **쓸모 있게** 돈다" 다.
