# 클립 원래 타이밍 전송본 (트리거 없음)

`transfer_v3/` 과 **같은 회로, 같은 임계값, 같은 5 mVpp, 같은 38,546 클립**이고
**시간 정렬만 다르다.** 이게 `docs/ask_analog_v4.md` 의 요청 1번이다 — 요청서를
쓰던 시점에 이미 받아놓고 있었다.

| | `transfer_v3` | **이것** |
|---|---|---|
| `trigger` | `first sample where any channel v_env >= vthr` | **`null`** |
| `tail_padding` | `0` | `null` |
| `columns` | 100 고정 | **`source_duration_10ms_bins`** |
| 패키지 해시 | `529bb9bf…` | `ea94c6b2…` |

## 시간 프로파일이 완전히 다르다

프레임별 평균 발화율:

| 프레임 | 트리거판 | **클립 원래 타이밍** |
|---|---:|---:|
| 0–9 | **56%** | 1.0 → 3.9% |
| 40–49 | 2.2% | **27.9%** ← 봉우리 |
| 90–99 | 0.4% | 3.3 → 1.5% |

트리거판은 앞으로 몰려 뒤 60프레임이 비어 있었다. 이쪽은 **가운데가 봉우리인
종 모양** — 1초 클립 안에 놓인 음성의 모습이다.

## 길이가 가변이다

90.7% 가 정확히 100열이고, 나머지는 33~99열이다 (1초보다 짧은 wav).
`data/analog_spectrogram.py` 가 **뒤를 0 으로** 채운다 — `data/speech_commands.py`
의 `_fix` 가 파형에 하는 것과 같다(`F.pad(wave, (0, length - n))`). 가운데 정렬로
채우면 시간축이 원본과 어긋난다. 전체의 9.3% 가 해당한다.

## 데이터 상태

죽은 채널 0개, 포화 0개. 발화율 2~20% (평균 14.4%), **9.26 / 16 비트**
(트리거판 9.05, 우리 시뮬 11.16).

## ⚠️ 선형 프로브를 이 데이터에 쓰지 말 것

| | 트리거판 | 클립 원래 타이밍 |
|---|---:|---:|
| 선형 프로브 (전체) | 0.577 | **0.377** |

**데이터가 나빠진 게 아니다.** 선형 모델은 (채널, 프레임) 위치마다 고정 가중치라
단어가 시간축에서 움직이면 못 따라간다. 트리거판은 온셋 정렬이라 선형 모델에
유리했을 뿐이다. CNN 은 합성곱이라 이동에 강건하므로, 여기서 프로브는 **천장이
아니라 바닥**이다.

즉 `transfer_v3` 때 "프로브 0.577 이 데이터 천장"이라고 읽은 것은 **정렬된
데이터에서만 성립하는 읽기**였다.

## 학습

```bash
python -m train.train --config configs/base.yaml --tag an_native \
  model.n_classes=10 model.stages.conv4.channels_abs=10 \
  data.analog_csv_root=analog/AFE_board/transfer_v3_native/spectrogram-native.tar.gz
```

비교 대상: `an_bn` 0.730 (트리거판), `bd_base` 10클래스 재집계 **0.826~0.841**.

이 런이 **시간 정렬 변수를 지운다.** 남는 차이는 검출기·비교기뿐이고, 그게
"우리 시뮬 vs 실제 회로"의 첫 단독 숫자다.
